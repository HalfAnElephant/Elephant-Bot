# Task implementation

Core `TaskService` is the sole database writer. Task acceptance and its confirmation Outbox intent share one transaction. Completion, manifest validation, terminal state, slot release and final Outbox intent are separated from model/network execution. Task result delivery uses the existing Outbox and remains independent of execution retries.

`TaskService(db, clock, outbox, archive_root=None, stop_verifier=None)` exposes `accept`, `get`, `cancel`, `retry`, `add_input`, `claim`, `renew`, `append_event`, `submit`, `stopped`, `uncertain`, `reconcile`, `recovery_status` and `recover`. Default archive location is beside the Core DB under `artifacts/`. The supervisor `--archive` must match. Trusted admin/owner contexts may explicitly submit research tasks. User-supplied role claims have no authority. Query is current-conversation scoped, cancellation is requester or trusted admin/owner scoped. Members cannot submit by default. Persistent permission snapshots include requester, trusted context identity source, role, conversation, tools, quota, policy and expiry.

Limits are one global runner, two queued tasks per requester and five per conversation. A least-recently-served conversation is selected before creation time. Slots remain reserved through lease expiry and unconfirmed stops. An expired run becomes `NEEDS_RECONCILIATION`, retaining its slot. The system deliberately has no automatic rerun of a possibly live runner. Admin reconciliation requires a root-owned stop marker, the latest reserved run and no newer fencing owner. It creates a new recovery run/fencing token before committing a validated spool result. Cancellation/expiry suppress recovery success. Closing a proven stopped task without a result releases its slot. Exact session resume remains disabled. Retry creates a linked new Task and retains old history.

`jobs.api.internal_router(service, token)` exposes authenticated HTTP endpoints beneath `/internal/tasks/`. Token length must be at least thirty-two characters and belongs only to Core and Supervisor. Deploy the router behind the Core Unix socket. Worker requests include worker identity, run ID and fencing token. Event append adds stable event ID and contiguous sequence. Duplicate identical event/result submissions are acknowledged. Conflicting submissions fail.

Run the independent supervisor with `python -m qqbot.jobs.worker --socket SOCKET --token-file FILE --pi ABSOLUTE_PI --workspace ROOT --spool ROOT --archive ARCHIVE --runner-mode systemd --model MODEL --model-endpoint CHAT_COMPLETIONS_URL`. Production paths are fixed by the launcher and checked on startup. Use `--runner-mode local` for protocol development. Set a dedicated `QQBOT_RUNNER_OPENAI_KEY` in the supervisor environment. It stays in the supervisor proxy. The runner receives separate per-run temporary tokens and a generated isolated model configuration. Do not reuse a deployment operator's personal Pi profile or credentials.

Results are fsynced into a bounded twenty MiB supervisor spool before submission. A lost success response can be safely replayed against the identical committed result. An expired fencing token cannot change a terminal state. Stale spool is retained for explicit reconciliation and blocks starting another model run, preserving evidence. Spool is a delivery journal, with no alternate domain database. Supervisor normalizes and fsyncs bounded accepted/progress/tool/error/result-ready events and source references into a per-run event spool. It forwards contiguous events to Core for the management timeline. Event text and source bodies are omitted from the timeline journal. Total event/result spool is twenty MiB, with at most five thousand events per run. Identical acknowledged replay is safe. Explicitly reconciled stale spool is discarded only after Core acknowledges the new ownership outcome.

## Verification and remaining acceptance

Targeted tests exercise queue limits/identity, fencing, persistent slots, cancellation and late-result suppression, result/outbox idempotence, fairness, artifact symlink/hardlink traversal, spool bounds, public-address restrictions, proxy quotas/revocation, and real Pi get_state/three-round research tool RPC with an offline mocked upstream. They do not require provider credentials.

Target-host acceptance should exercise real Pi research, public search and page retrieval, report creation, archive hashing, authenticated download, QQ result delivery and running-task cancellation. Run the Linux isolation probe under supervisor umask 0077 to verify workspace, credential, network and descendant-cgroup boundaries.

Research quality still requires human review. New hosts must verify their own isolation policy. Verify reboot recovery on the target deployment. Local mode uses the supervisor UID and remains a protocol-development path. Append-input, automatic session resume and general execution tools remain disabled.
